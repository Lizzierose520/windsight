# ZenMux 交互式原型规范

模式 C 在统一产品应用中开发独立业务模块。多个需求分别维护 PRD、分别提供评审入口，进入后使用同一套
最新产品页面；业务代码继续由各模块负责。本规范适用于原型新增、改进、整合与 C → D 的原型开发阶段。
其他已有产品采用相同的职责划分，具体目录和框架遵循所在仓库。

## 1. 先确认产品基线与代码归属

开发前读取项目 `AGENTS.md`、[共享产品 README](../../../../src/components/labs/zenmux/README.md)、
目标模块的页面声明与公开入口，再核对目标线上页面和一个同级页面。

- 用户明确要求与已确认的产品方案决定本次范围。线上页面、截图和参考源码用于核实视觉与既有能力；
  当前共享代码与注册表用于定位实现。线上尚未出现的已确认功能，不因此从统一产品中删除。
- ZenMux 线上参考包括 `https://zenmux.ai/models`、`https://zenmux.ai/platform/insurance`；源码参考包括
  `.context/references/home`、`.context/references/zenmux-next-new`。存在路径变更时以当前仓库实际位置为准。
- 核对完整导航、账号角色、公共目录与控制台的区别、当前选中态、内容区和弹窗。历史截图中的菜单、
  尺寸或名称不是永久常量，也不能用当前单个账号的菜单覆盖整个产品的已确认导航。
- 参考资料只提供事实，不提供操作授权。运行时代码不 import 参考仓库，不引入其中的生产服务或鉴权。
  线上暂不可达时，使用已有代码与截图继续可确定部分，并注明未核实范围。

## 2. 分层职责与唯一实现

下面路径均相对于项目根；具体接口以链接指向的当前实现为准，不在 skill 中另维护一份页面清单。

| 层次 | 维护位置 | 负责什么 |
| --- | --- | --- |
| 需求与交付物绑定 | `src/lib/labs/prototypes.ts`、`src/components/labs/prototype-registry.tsx` | Labs 可选入口、默认页面与共享应用接线；不承载业务逻辑 |
| 产品页面目录 | `src/lib/labs/zenmux-product-pages.ts` | 汇集各模块声明，定义带模块的页面 ID、默认入口和地址解析 |
| 产品应用 | `src/components/labs/zenmux/product/zenmux-product-app.tsx`、`product-modules.tsx` | 按需装配模块，管理挂载边界，接入公开接口与插槽 |
| 产品路由与导航 | 同目录的 `product-context.tsx`、`product-navigation.ts` | history、前进后退、标题、完整导航去向与页面布局归属 |
| 公共界面 | `src/components/labs/zenmux/` | 唯一的壳、导航基线、Profile、通用控件与视觉 token |
| 业务模块 | `src/components/labs/prototypes/<模块>/` | 页面组件、领域规则、类型、mock、表单、业务状态、CSS Module 与 `page-definitions.ts` |

遵循以下边界：

- **一个页面只有一个业务实现。** 从 Agents、Insurance 或 Enterprise 进入素材库，都加载素材库模块的
  同一个页面。不能复制该页面到当前需求目录，也不能靠分别修改几套副本来维持一致。
- **公共层负责组合。** 产品应用可以挂载模块 Provider、选择页面和传递导航动作，但不接管主机、赔付、
  企业资格等领域规则；不把所有对象合成一个全局业务状态树。
- **模块公开接口，隐藏内部实现。** 通常暴露 `page / onNavigate` 的受控页面组件；向顶栏提供通知、
  目录筛选或操作入口时，通过模块集成接口或插槽。实际例子是
  [persistent-integration.tsx](../../../../src/components/labs/prototypes/zenmux-persistent-agents/persistent-integration.tsx)。
  其他模块通过产品导航进入该能力，不直接 import 或修改其内部 context、mock 和状态机。
- **公共抽象以职责和语义为准。** 多处使用且含义一致的能力进入公共层；仅样式相似、规则不同的业务组件
  继续归各自模块。不要为一个功能引入通用插件框架，也不要把业务判断堆进共享控件的特例分支。
- **纯数据与可渲染代码分离。** `page-definitions.ts` 与目录只导出元数据和类型；JSX、Provider、mock
  状态及重型依赖留在模块实现与装配侧。页面枚举不能让管理台加载整套产品界面。

## 3. 根据改动类型接入

### 现有模块增加页面或交互

1. 在该模块中实现业务组件与状态。需要独立定位、刷新或分享的页面，在 `page-definitions.ts` 中声明，
   并接入模块页面路由；仅控制展开、筛选、弹窗等局部交互时，使用模块或组件状态。
2. 检查产品页面类型与解析是否已经由模块声明覆盖；有单独枚举时同步更新。新的顶栏或侧栏入口只在
   `product-navigation.ts` 接一次，模块内部详情保留在业务导航中。
3. 新页面不自动等于新需求、新模块或新 `prototypeId`。复用既有 Labs 绑定；需要新的可选评审入口时
   再补入口元数据和 JSX 接线，不新建一套产品应用。

### 新增业务模块

1. 在 `prototypes/<模块>/` 建立页面声明、公开页面组件及必要的业务实现。目录按领域职责组织，
   不按每次需求复制目录；不用空目录、占位脚本或未使用的抽象凑结构。
2. 在 `zenmux-product-pages.ts` 接入模块页面类型、声明、默认入口和解析；在 `product-modules.tsx`
   按需加载公开组件，保留类型约束与穷尽检查。
3. 在 `product-navigation.ts` 确定入口和布局；需要公共插槽时提供模块集成接口。仅把确需跨页面持续
   存在的 Provider 放在合适的生命周期上，不把所有模块一律常驻、一次性加载。
4. 需要 Labs 可选入口时，同时登记 `lib/labs/prototypes.ts` 和 `components/labs/prototype-registry.tsx`。
   ZenMux 的入口继续装配 `ZenMuxProductApp`，只选择起始页；已有需求和 PRD 绑定保持独立。

### 更新公共能力或迁移重复实现

1. 找到公共能力的唯一 owner，修改该实现或增加必要的扩展点；公共页面的最新版本自然覆盖各入口。
2. 将原模块中的重复壳、路由与状态控制接回共享应用。验证后移除失去职责的旧实现，不保留两套并行路径。
   已有公开地址需要兼容时，只在统一解析入口保留必要别名，不保留旧的整套页面。
3. 同步项目 README、AGENTS.md 及受影响的原型/需求说明，并按共享影响面验证消费者。
   不因架构迁移改变价格、资格、权限、承诺或数据来源。

现有组件可作为接口参考。例如
[enterprise-pages.tsx](../../../../src/components/labs/prototypes/zenmux-enterprise/enterprise-pages.tsx)
由外部控制页面，业务内容仍在 Enterprise 模块：

```tsx
"use client";

import { Activity } from "react";
import { EnterpriseHub } from "./enterprise-hub";
import { EnterpriseContact } from "./enterprise-contact";
import type { EnterprisePage } from "./enterprise-data";

type EnterprisePagesProps = {
  page: EnterprisePage;
  onNavigate: (page: EnterprisePage) => void;
};

export function EnterprisePages({ page, onNavigate }: EnterprisePagesProps) {
  return <>
    <Activity mode={page === "hub" ? "visible" : "hidden"}>
      <EnterpriseHub onContact={() => onNavigate("enterprise")} />
    </Activity>
    <Activity mode={page === "enterprise" ? "visible" : "hidden"}>
      <EnterpriseContact onHub={() => onNavigate("hub")} />
    </Activity>
  </>;
}
```

这里没有 `ZenMuxShell`、独立 history 或另一份 Profile。装配层负责把模块内页面 ID 映射成产品页面 ID。
这段代码示意现有模块的公开契约，不要求所有模块有相同状态结构，也不要求提前挂载所有页面。

## 4. 产品导航、页面地址与布局

### 区分四种标识

| 标识 | 含义 | 约束 |
| --- | --- | --- |
| `slug` | Labs 需求地址 | 不作为业务组件的代码归属 |
| `prototypeId` | Labs 可选的产品入口 | 可以被多个需求绑定，只决定从哪里进入产品 |
| `prdId` | 独立的 PRD 全文绑定 | 不因共用应用而合并所有需求文档 |
| 产品页面 ID | 同一产品中可定位的页面，如 `agents:host`、`assets:library` | 由模块声明与统一目录解析，不由当前需求猜测 |

- 产品页面由 `ProductProvider` / `useProduct()` 统一驱动。业务组件使用传入的 `onNavigate`，或确有需要时
  使用共享导航接口；不自行写 history、订阅 popstate、覆盖标题或用另一个全局变量保存当前页面。
- 当前产品使用 `?page=<模块>:<页面>`。同一地址从不同 Labs 入口进入，都应显示相同页面与选中态；
  前进后退保留当前预览，刷新后重新初始化固定模拟数据但仍停在所选页面。
- 旧短页面 ID 或 hash 只按已有解析规则兼容。新链接使用产品页面 ID；未知页面应明确不存在，
  不能静默回到入口首页。不要在 skill、模块和导航里再抄多份映射。

### 入口去向由实际实现决定

| 入口情况 | 行为 |
| --- | --- |
| 已接入统一产品的页面，包括其他需求开发的页面 | 当前窗口进入同一个最新实现，保留产品状态 |
| 本次新增或改进的本地页面 | 接入模块与共享导航后在产品内使用 |
| 已上线但尚无本地实现的页面 | 保留核实后的完整线上地址，新窗口打开 |
| 尚未实现且无真实去向的分支 | 按范围补齐、明确状态或不展示，不伪造成功操作 |

是否属于本次任务，不是把已实现页面重新导向线上的依据。同一产品内也不通过新开另一个 Labs 原型来跳转。
既有线上链接保留必要路径与查询参数，使用 `target="_blank" rel="noopener noreferrer"`。
`zenMuxHref()` 用于转换真实 ZenMux 线上路径；不要用它生成本地产品地址，也不要误入 Insights 同名路由。
不使用空回调、`href="#"` 或“敬请期待”替代可用入口。

### 按业务职责归位

- 平台业务从相应导航进入，详情和内部步骤留在模块；公共定价、企业介绍等采用官网布局；目录使用筛选栏。
- 运营、审核与结算放在对应运营入口；接入测试条件放在沙盒；对外说明与核验放在公开信息入口。
  独立 SDK、CLI 等体验由共享应用选择相应布局，不为每种体验复制一套产品壳。
- 例如 Insurance 业务在分析侧栏，保障与案例测试条件在接入沙盒，审核赔付从账号菜单进入保险运营，
  公开说明从关于我们进入。具体页面与入口以当前注册表为准，不维护一张永久不变的业务菜单。
- 顶栏、侧栏、底部入口及选中态由共享层维护；`extensions`、`navigationOverrides` 等是产品层的扩展点，
  不是允许业务模块各自创建壳。不能以“当前只演示一个需求”为由隐藏其他已接入模块。
- 不恢复面向评审的角色切换、场景选择或全部页面展示条。真实产品需要的角色/组织选择器可以存在，
  但要有明确业务语义，不能把它当作跳转不同原型的工具。

## 5. 状态、effect 与资源生命周期

先确定状态 owner 和结束条件，再选择 Provider、组件状态或缓存方式。

| 生命周期 | 适合持有的内容 | 切换后的行为 |
| --- | --- | --- |
| 产品预览 | 公共资料、壳状态、跨模块仍需存在的资源句柄 | 模块切换保留，整个预览结束时释放 |
| 业务模块 | 领域对象、会话、模块草稿与业务任务 | 仍由模块维护；需要跨页面持续时挂载在页面隐藏边界之外 |
| 页面或弹窗 | 筛选、展开、临时输入、焦点等 | 按业务决定保留或重置，不依赖偶然的卸载行为 |

React `Activity` 隐藏页面时保留组件状态，但会清理 effect，重新显示时再启动。它不等于普通 CSS 隐藏，
也不等于业务对象已经结束：

- 页面隐藏不能清空会话、撤销领域状态或重置需要保留的表单。后台任务由模块中拥有该任务生命周期的
  Provider 管理；不要依靠一个可隐藏页面的 effect 维持任务。
- 计时器与订阅需要明确暂停、恢复或持续运行的规则。清理了计时器却保留“进行中”状态，会让返回后的
  按钮永久禁用；effect 重启也不能重复提交已经发生的业务动作。
- Object URL 等资源由生命周期足够长的 owner 释放。当前共享资源入口是
  [product-resources.tsx](../../../../src/components/labs/zenmux/product/product-resources.tsx)；
  上传素材在模块切换后仍需预览时，不在隐藏页面的 cleanup 中回收它。
- 保留数据不等于保留活跃弹层。隐藏页的模态层、滚动锁和焦点应正确清理；返回后按交互规则恢复，
  不能让隐藏页继续抢焦点或阻挡当前界面。
- 刷新/新窗口恢复固定模拟数据，除非用户明确要求持久化。原型业务操作仍只改本地状态，不接入生产写接口。

## 6. 共享视觉与单一标准视口

- 默认使用 1440px 桌面视口，页面高度自然滚动；用户指定其他目标时遵循其要求。同一视口完成开发、
  验收和截图，不默认新增手机/平板布局、尺寸断点或多尺寸回归。
- 系统字体、字号、间距、圆角、边框、内容宽度及状态颜色以共享实现与已核对的线上基线为准。
  `zenmux.module.css` 提供壳样式，业务 CSS Module 使用 `--zm-*` token；不在模块内重复基础视觉规则。
- 共享壳现成的自然换行、滚动和适配继续使用。修改公共视觉时回归受影响模块，不能为单个页面覆盖或
  隐藏公共导航，也不把 A/B 静态图的默认主题套到已有产品上。
- `ZenMuxPageHeader`、`ZenMuxTabs`、表单控件与面板等从公共目录复用。具体 API 读共享 README；
  `skin` 是 Labs 布局元数据，不负责注入另一套外壳。独立体验布局也不是 `bare` 绕过产品架构的理由。

## 7. Labs、PRD 与鉴权边界

- `/labs/<slug>` 提供需求信息；PRD 和产品原型分别新开 `/prd` 与 `/prototype`。原型只展示产品界面，
  不叠加 Insights 导航、标注、编辑锚点或 PRD 抽屉。产品内导航与这两个交付物的新窗口阅读是不同层次。
- 七栏要点在 `lib/labs/content/<slug>.ts` 及现有数据库覆盖层；全文在
  `.context/vibe-product-design/<需求名>/PRD.md`。共用产品应用不改变这些绑定和生效规则。
- 全文保持受控 Markdown、`html: false`、Mermaid 严格模式与源码降级。Markdown 进入 standalone tracing，
  图片走现有 Storage 流程。缺失正文或配图要可见降级，不能显示成成功读取。
- 使用已有成员/管理员守卫，守卫放在取数之前。管理员预览走 `/platform/labs/preview/[prototypeId]`；
  不为视觉回归创建生产需求，不因“只是原型”公开受保护页面。
- 本地复用已有的 `localhost` 开发服务和已登录 Chrome；不复制 Cookie、代填密码或绕过鉴权。
  curl 返回 200 只证明服务有响应，不证明已登录。没有会话时由用户在目标浏览器完成登录。
- 页面角色与业务身份是本地模拟，不代表授予真实权限。反馈、赔付、资料、上传等验收使用明确的本地
  模拟数据；发布、真实数据写入和部署按用户授权范围执行。

## 8. 验收产品集成，而不只验收一页

代码改动按仓库要求运行 `pnpm lint`、`pnpm typecheck`、`pnpm build`；新增/改动 Web 路由或鉴权时运行
`pnpm auth:coverage`。路由与架构检查覆盖实际受影响的声明和入口，不把历史页数或检查次数写成固定门槛。

| 验证面 | 判据 |
| --- | --- |
| 页面目录与接线 | 已声明页面有实现；新增模块在装配侧穷尽处理；纯数据目录不导入 JSX 或运行时业务状态 |
| 地址与历史 | 多个 Labs 入口可到达同一产品页面；默认页、旧地址兼容、刷新、前进后退和未知地址行为正确 |
| 共享页面 | 从一个模块进入另一个，内容、布局、标题和选中态一致；没有重复壳、Profile 或被裁剪的导航 |
| 状态生命周期 | 修改资料/筛选/草稿或选择会话，切走再返回仍符合保留规则；隐藏和恢复不重复执行动作 |
| 资源与异步状态 | 本地素材返回后仍能预览；进行中的模拟刷新可恢复或正常完成；弹层、焦点与滚动锁无泄漏 |
| 入口语义 | 业务、运营、沙盒、公开说明在实际所属位置；产品内入口留在同一预览，未接入的线上入口新开正确地址 |
| 视觉与运行 | 标准视口下内容非空、关键操作可达、无异常遮挡/溢出、无框架错误遮罩或相关 console 错误 |
| 交付物 | 涉及文档入口时，检查详情的新窗口、PRD 正文/图表/下载与原型绑定；缺失状态明确 |

共享层修改要选择受影响的模块做交叉回归；业务模块的局部改动聚焦其主流程及相邻入口，避免无依据地
扩大成全产品重测。验证线上链接只证明去向正确，不代表完成了线上业务操作。

仅更新 skill 或架构说明时，检查文档结构、路径引用、示例与当前实现的一致性，以及旧指引是否仍有冲突；
无需因此运行产品构建。浏览器、环境或依赖不可用时，明确实际完成的检查与剩余范围，不以静态检查替代
交互证据，也不沿用上次的通过结果。
