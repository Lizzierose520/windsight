# 模式 D · 原型驱动 PRD 方法与模板

适用：先用 Vibe Coding 做出想要的产品，再从代码、截图、演示或录屏反推完整需求。
产出：`.context/vibe-product-design/<产品或需求 slug>/PRD.md`，由模块源文档确定性合并生成。
已有匹配文档先完整读取并迁入或复用对应源文件，不直接修改已生成的成稿。

本文依次说明材料探索、整体建模、隐含需求提炼、全局收敛、写作模板、方法示例与完成标准。
只在模式 D 读取；不要求先完成 A 的六章、B 的静态图流程或 C 的 Labs 开发。
执行时同时读取 [原型 PRD 交付流水线](原型PRD交付流水线.md)：按模块分写、关键截图先忽略 Git 再保存、
上传 Supabase Storage、脚本合并、全局 review 后回改来源并反复合并，最终只有一份 PRD。

## 1. 工作目标：让可见的产品成立

用户已经表达了“最终想要什么样的产品”。你的工作是以产品经理的判断，解释这个产品服务谁、交付什么
价值、依靠什么策略和规则运行，以及在真实使用条件下怎样保持一致、可用和可验收。

进行两轮思考：

- **发散解构**：从每项产品能力追问其承诺、成立条件、业务对象、状态变化、资源约束和上下游影响。
  页面没有展示失败、延迟、争议或并发，不代表这些需求不存在。
- **收敛建构**：把发现归入业务模块，确定规则归属、统一概念和生命周期，剔除无关扩展，连成完整的
  产品体系。最终正文是产品的运行逻辑，不是探索记录或一串问题。

以“云主机定价”为例：看到小时单价后，要理解计量对象、开始与停止条件、计费粒度、结算周期、免费
权益、额度保护和其他费用的关系。写“三张价格卡片，右侧有购买按钮”没有完成这项工作。

**详细程度取决于产品决策的复杂度，不取决于截图数量。** 一个模块可以有多个页面、页签和弹窗；
一个页面也可以同时呈现多个模块的结果。界面结构、组件结构与需求结构不必一一对应。

## 2. 先理解材料，建立证据边界

### 2.1 定位范围与基线

先读用户给出的目标、路径和链接，再查已有 PRD、相关决策和项目约束。提炼本次产品范围与关键模块，
优先使用已经提供的材料；代码、截图、演示任选一种即可启动，按需要互相补充，不要求用户集齐材料。

记录足以定位本次依据的信息：代码路径与版本（含相关未提交改动）、截图文件与来源、演示 URL 与观察
日期、录屏片段时间、已有 PRD 版本。不要把正在修改的工作区写成已发布版本，也不要把不同版本的材料
默默拼成一个同时存在的产品。版本冲突时先辨别各自意图，再确认会改变需求的分歧。

在 ZenMux 中涉及现行产品政策时，使用 `zenmux-context` 核对官方文档，结合用户本次明确决策；
官方现状与新原型的目标分别表述，不用现行文档抹掉用户明确提出的新设计，也不用原型代替现行政策。

### 2.2 按材料类型探索

| 材料             | 应做的探索                                                                                                                          | 能证明什么、不能证明什么                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 原型或产品代码   | 从入口追踪相关组件、状态管理、类型、计算、校验、权限条件与 mock；重点读影响业务结果的逻辑。用 `rg --files`、`rg` 定位，按需追踪依赖 | 能确认这份代码表达或实现的行为；不能仅凭常量、注释或前端校验确认生产策略和保障           |
| 可用演示地址     | 用浏览器实际走完关键模块的代表性业务路径，观察操作前后状态、返回/重进后的持续性、已提供的异常与空态；必要时与源码互证               | 能确认本次实际观察到的行为；首屏截图或静态 HTML 不能证明后续交互、持久化、权限与真实计费 |
| 产品截图或设计稿 | 实际读取图片，结合名称和前后状态理解业务含义；识别价格单位、资格、对象关系、状态和承诺                                              | 能确认可见内容；不能断言未展示的交互、失败分支、实际性能或后端能力                       |
| 录屏或演示视频   | 在工具可用时查看关键片段与状态变化，记录时间点；识别剪辑、跳步和未展示条件                                                          | 能确认片段中的路径；演示时长不等于性能目标，成功一次不等于可靠性保障                     |

先贯穿整体，再深入有业务含义的分支；无需遍历每一个装饰控件。若材料只覆盖定价模块，就深入该模块，
对其他模块写清必要依赖，不能伪称已完成整个产品的分析。

有代码和可运行页面时结合阅读与交互验证。演示不可达、浏览器无登录态或视频不可读时，使用其他已有
材料继续推进，明确未观察范围。能从项目找到的材料先自己查；必须补充的入口或业务决策再简短询问。
只有截图也可以产出有用的 PRD，但不能写“已验证所有交互”。

探索默认只读。确认是本地 mock 的操作可用于理解状态；真实环境只做无副作用观察。复用已有登录态，
不读取、复制 Cookie 或代填密码，不为分析需求创建真实资源、产生费用、发消息或删除数据。已有授权的
测试按其明确范围执行。本仓库浏览器、服务复用与鉴权回归要求以仓库 `AGENTS.md` 为准。

### 2.3 分清观察、需求与判断

| 类型                                       | 处理方式                                                                               |
| ------------------------------------------ | -------------------------------------------------------------------------------------- |
| 用户已确认要求或适用于目标版本的已确认规则 | 写成规范性需求，保留来源；不得被旧截图、mock 或实现缺陷悄悄覆盖                        |
| 直接观察到的页面/代码行为                  | 作为理解产品意图的证据，在模块依据或具体规则处说明“原型当前……”；不自动升级为已确认政策 |
| 使已知能力成立的必要补充                   | 主动提出具体的产品要求，尚未确认时标 `[建议]` 并说明理由和影响；不要只列“是否需要考虑” |
| 证据缺失、材料冲突或关键策略未定           | 标 `[待确认]`，给出推荐方案、取舍及受影响规则；事实前提的暂定推断可标 `[假设]`         |

用户最新明确决策优先；已有 PRD 需核对适用版本。源码和运行效果可用于互相验证，但都不是天然的
“需求最高依据”：实现可能有缺陷，演示可能省略流程。截图里没有某个规则，也不能作为删除原有规则的依据。

关键未知只标在相关段落和最终决策表，不必给每句话加标签；来源索引保持简短可定位。记录尚未确认的
事项是为了让用户作出决策，不能借“证据不足”把整份文档退化成问题清单。

## 3. 从完整产品划分业务模块

在内部先建立整体认识，再写各模块，避免读完一个页面就立即写一份孤立的需求。

1. **产品价值与完成条件**：用户是谁，最终完成什么任务，在哪种情况下认为成功。本次材料只能证明
   产品意图时，不虚构用户调研、市场数据或转化率来充当背景。
2. **核心业务对象及其关系**：例如账户拥有主机，主机承载已安装 Agent，Agent 产生会话，会话消费资源。
   分清目录条目、已安装实例、运行会话这类相似但不同的对象；描述业务含义，不设计表结构。
3. **主业务链**：从获取资格/选择方案到使用、变更、退出及结果留存，跨模块梳理成功、失败与恢复路径。
4. **模块职责**：按用户目标、业务对象生命周期和策略归属划分，把同一业务闭环中的子页面合并。
   顺序按读者理解产品的依赖关系安排，不照路由、目录树、截图编号或点击顺序抄写。
5. **共享规则归属**：每条规则只有一个定义位置。有自然归属的放在所属模块，无自然归属的产品级规则
   放在全局章节。其他模块引用规则并解释自身受影响的行为，不再复制一份定义。

例如，“云主机定价”可以统管价格说明、用量估算、购买确认与计费方式说明；“云主机管理”统管资源
生命周期和保留行为。管理模块定义“什么时候已停止”，定价模块引用该状态定义费用变化；费用保护
触发停止时，管理模块再引用定价模块的触发条件。这样的相互约束必须闭合，不能只写“详见其他模块”。

区分**规则依赖**与**执行先后**：模块可以相互约束，但执行流程必须有明确触发点，不能形成“双方都等
对方先成功”的循环条件。发生冲突时回到规则定义处解决，并同步所有引用和验收结果。

## 4. 从可见能力提炼隐含需求

### 4.1 推理链

对每项有产品意义的能力沿下面的链条展开，在内部完成推导，正文写收敛后的结论：

```text
可见能力 → 用户要完成什么 → 产品承诺什么 → 承诺成立需要什么
        → 业务规则与生命周期 → 异常和边界 → 上下游影响 → 可验收结果
```

例如看到“停止主机后保留工作区”，应追问并形成需求：什么叫停止完成、哪些内容保留、哪些执行中断、
停止失败如何判断、何时变化费用、再次启动能恢复什么、其他会话如何获知。最终写成连贯的停止与恢复
规则，而不是“点击停止按钮弹出确认框”。

### 4.2 按模块选择推导维度

下表是探索透镜，**不是每个模块都要填满的通用清单**。只展开与当前产品承诺和使用场景直接相关的维度。

| 维度             | 应提炼出的产品需求                                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 策略与权益       | 服务对象、准入资格、套餐/版本差异、限额、优先级、继承关系、兼容与变更政策；解释为什么这些规则能支撑产品定位                                       |
| 计量、计费与结算 | 收费对象、包含/排除项、单位、时间边界、精度/舍入、价格生效版本、权益抵扣顺序、超用与预算、失败/不可用时段处理；区分估算、累计用量、应付和实际扣费 |
| 对象生命周期     | 创建、准备、可用、运行、暂停/停止、失效、删除等实际适用状态；状态成立条件、转换触发、取消/重试、不可逆后果                                        |
| 资格与权限       | 谁拥有对象、谁能使用/变更/停止、什么授权会被继承、权限失效如何影响已有任务；界面不可见与业务不可操作不是同一个条件                                |
| 时间与并发       | 生效时点、进行中的操作、重复请求、多端同时操作、乱序反馈、断开与重连；解释用户最终应得到什么结果                                                  |
| 数据与结果       | 输入/配置的约束与默认值、跨页持续性、保存与恢复、删除/过期后的结果留存、统计口径与时效；不写存储方案                                              |
| 服务质量与运营   | 响应与完成时间、任务连续性、可用性、容量边界、失败可辨识性、用户自助恢复、费用可解释性，以及必要的发布/迁移约束                                   |

不是每个空白都应新增功能。例如，为“停止后保留文件”明确保留范围属于需求补全；再加一个付费备份
市场可能已经是新能力。将必要条件写进当前模块；可选增强标出范围与建议，不以“完整”为由扩大产品。

### 4.3 写成可执行的产品规则

先解释策略，再展开规则。例如定价模块还应回答价值如何计价、为什么按主机或按 Agent 收费、服务如何
分层、免费权益与超用如何引导持续使用，以及与其他产品付费方案如何协同。按材料与产品目标给出判断，
推导出的策略理由标为推论或建议，不编造商业实验、盈利数据或决策历史。

重要规则应能回答：**谁 / 在什么前提下 / 发生什么事件 / 按什么规则和时间生效 / 得到什么结果 /
失败或重复时怎么办 / 影响哪些模块 / 如何验收**。简单规则用一段话即可；复杂的费用、状态和权限关系
可用小表格或业务流程图，不为每条规则机械展开九个字段。

- 先解释模块整体策略，再按业务主题展开。例如定价模块按“费用构成 → 计量与抵扣 → 变更与结算 →
  费用保护”组织，不能按“卡片 → 开关 → 弹窗”组织。
- 规则编号使用已有业务编码；没有时可用 `BIL-01`、`CAT-01`、`STU-01`、`HST-01` 等模块前缀。
  编号表示稳定的需求或规则，不表示按钮，不随页面顺序变化。已经发布/引用的编号不复用给别的含义。
- 金额公式必须解释单位、适用对象、周期、包含项、排除项和边界；只有成立条件都已明确才给出确定公式。
  未确认的价格、抵扣顺序、封顶范围不得“按行业惯例”补成现行政策。
- 重复提交、超时或断连时应描述“用户能否确认结果、是否重复创建/收费、如何继续”，不要越界设计
  数据库事务、缓存、消息队列、幂等键协议等实现方案。
- 引用界面中影响业务理解的文案可以保留原义，例如“预计费用”“永久删除”；颜色、间距、卡片形状
  和控件坐标不属于本模式正文。必要时附原型链接，避免用长图注代替需求。

### 4.4 性能与质量要求要能判断

从真实使用目标推导，区分“请求已被接收”“资源准备完成”“任务执行完成”“结果已同步”。浏览器
即时更新、mock 的 `setTimeout` 或一次演示耗时不能成为上线性能依据。

涉及定量要求时交代：**适用场景与规模、起止事件、指标/分位数、目标值、统计窗口、未达标时的产品
行为和验证方法**。优先采用已有明确目标；需要新目标时给出有理由的 `[建议]`，未能确定阈值就明确
待确认项，不能把 99.99%、1 秒响应等通用数字包装成已承诺 SLA。

即使阈值未定，也应写出可确定的产品行为。例如“长任务被接收后可离开页面，重新进入可查询同一任务
的当前状态和结果；连接中断不能直接显示任务失败”是有价值的质量要求。它是否属于本产品的已确认
行为或建议，仍需按证据标注。涉及任务或资源时，把前端连接状态与实际运行状态分开定义。

### 4.5 澄清不取代产品判断

先从材料找答案，再向用户澄清会改变商业含义、资源归属、数据后果或核心行为的关键分歧。每次问题给出
背景、推荐方案、取舍和影响；已经明确的决定不再询问。继续完成不依赖答案的内容。

用户授权直接决定时，在授权范围内形成具体方案；没有这种授权的关键缺口保留 `[建议]`/`[待确认]`。
输出需要包含可评审的建议内容，不能只写“计费策略待定”“性能待定”。建议可以待确认，推理不能缺席。

## 5. 写完模块后，按整体收敛

沿主业务链逐段校验同一对象、同一时刻、同一行为在所有模块中的含义：

- **术语和归属**：市场条目、已安装实例与会话是否分清；“用户”“账户”“工作区”的边界是否统一。
- **状态和生效**：购买成功、权益生效、安装完成、资源可用、任务可执行是否被误当成同一个状态；失败
  与取消后哪些结果保留，谁定义这个结果。
- **时间和金额**：起止事件、时区、周期、抵扣、封顶、估算与实际账单是否一致；费用只由相应计费
  对象产生，不能在多个模块中重复计算或消失。
- **异常的传播与恢复**：上游失效时下游显示什么、还能做什么；恢复后是否需要重试、会不会产生重复
  实例/费用；不能一个模块已停止而另一个仍承诺继续运行。
- **规则的引用与变更**：每项共用策略只定义一次。修改主机停止策略时，同步检查计费、会话、数据保留
  和验收，不只改管理模块那一段。

验收围绕业务结果写 Given / When / Then。至少覆盖当前核心链中的成功路径、关键失败与恢复路径；
按实际风险选择组合，不穷举每个控件。未确认策略对应的验收应标明条件或待定，不能写成已验证结果。

去掉画面后，读者仍应能理解产品如何运行；换一种布局后，主要业务规则仍应成立。这两项是检查正文
是否陷入看图说话的直接方法。若规则依赖用户确认、资格提示等必要交互，保留其业务目的与发生条件。

后续原型迭代时，从变化的业务能力追踪受影响规则及其上下游，回改对应源文档，再合并、再全局审阅。
纯样式变化通常不改
业务需求；页面暂时省略某项内容也不自动删除旧规则。已经确认的策略若与新原型冲突，明确差异及建议，
不因“代码更新了”就静默改写政策。

## 6. 模块源文档与最终 PRD 结构

同一产品最终只有一份 `PRD.md`，实际写作按业务模块分成源文件，在 `prd.config.json` 登记顺序。
下面展示最终成稿的阅读骨架，**不要照此直接写入 PRD.md**：每个业务模块对应一个源文件，产品整体、
共同规则、全局验收与决策也分别维护，具体目录与清单见交付流水线。源文档使用唯一一级标题，内部
标题不手写跨模块序号，合并器统一生成编号。模板编号只表示阅读层次，不是必须照抄的源标题。

每个模块只配能支撑关键结论的实际原型截图，放在相关规则、状态或边界说明附近；截图上传后源文档
使用稳定 OSS URL。图注解释业务结论，布局和样式仍由原型表达。源文档可以分别撰写，但合并后必须
作为一个完整产品进行 review，不能把“每篇各自检查过”当成最终全局审阅。

```markdown
# <产品名称> PRD

## 文档信息

- 版本、实际状态（草稿 / 待评审 / 已评审）、本次范围。
- 材料基线：原型/源码版本、观察日期、已有 PRD；注明仅观察到的范围。

## 变更记录

| 日期       | 版本       | 维护人       | 关键改动                         |
| ---------- | ---------- | ------------ | -------------------------------- |
| <实际日期> | <本次版本> | <真实维护者> | <实际补充的模块、规则和关联影响> |

## 1. 产品整体

### 1.1 用户、问题与产品目标

产品帮助谁在什么情境下完成什么任务；哪些结果代表成功。

### 1.2 本次范围与边界

覆盖哪些业务模块；已确认范围、必要补充与可选扩展分开。

### 1.3 核心概念与模块关系

定义业务对象、归属和关系。用简短表格或业务图解释模块职责及上下游结果。

### 1.4 端到端业务主线

从开始使用到完成、变更与退出的完整链条，概述主要异常与恢复分支。

## 2. 产品级策略与共同规则

只定义确属产品级的共同规则；有自然模块归属的策略在该模块完整定义，此处引用。
说明规则优先级与适用范围，避免各模块各自解释。已确认与建议中的策略明确区分。

## 3. <业务模块名称>

### 3.1 目标、范围与上下游关系

这个模块承担什么责任、接受哪些前提、交付什么结果；用一句话关联参考原型范围。

### 3.2 核心策略与业务规则

按有意义的业务主题展开，给出规则编号、条件、结果和必要理由。
引用共用规则；重要推导注明材料依据，新增建议标注其状态。

### 3.3 生命周期、异常与边界

本模块对象/结果的状态流转、生效时点、失败/取消/重试、恢复与不可逆后果。
其他模块定义的生命周期直接引用，说明本模块如何响应。

### 3.4 质量要求与验收

本模块特有的性能、容量、持续性、准确性等要求及适用条件。
按规则写可观测的 Given / When / Then；共用质量目标引用后文。

## 4. <下一个业务模块名称>

```

变更记录的新条目放在最上面，历史条目内容保留。新建 D 文档把记录放在文档信息源文件中，不生成
`PRD-final.md`。已有分章需登记为当前来源，选定一套合并脚本；不能两套流程轮流覆盖，也不能只改生成文件。

按需沿用共同的 P0–P3 分级；工作量和技术复杂度只有在有用且有依据时标，不凭截图替研发确定工期。

## 7. Persistent Agents 方法示例

以下用于示范如何提炼和组织，**不是当前 ZenMux 的政策、价格或已核验 PRD**。真实任务必须读当时的
原型、正式规则和用户决策，不能把示例复制为需求事实。

### 7.1 从关键页面归纳模块责任

| 观察入口                         | 业务模块         | 应补全的核心内容                                                                | 对其他模块的约束                                           |
| -------------------------------- | ---------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 价格说明、费用估算、购买确认     | 云主机定价与计费 | 费用边界、计量起止、粒度与舍入、周期、抵扣、封顶/预算、变更和结算；哪些数是估算 | 为管理、市场与 Studio 提供同一套收费和权益口径             |
| 目录、Agent 详情、安装过程       | 智能体市场       | 可用资格、版本/模型兼容、安装目标、重复安装、安装失败与上下架对已安装实例的影响 | 向主机交付明确的安装结果；向 Studio 提供可执行条件         |
| Agent 选择、任务执行、结果查看   | Studio Agents    | 目录可见与可运行的区别、会话条件、任务连续性、断连/重连、失败重试、模型消耗归属 | 服从主机可用状态、安装结果及费用边界；回传可解释的执行结果 |
| 主机概览、启停、配置、用量与费用 | 云主机管理       | 资源归属、就绪与运行定义、停止/删除后果、配置生效、文件与进程保留、恢复条件     | 向定价提供计量状态，向 Studio 提供可执行性与中断/恢复结果  |

### 7.2 一个可见承诺，反推一组相互衔接的需求

假设本次材料明确表达了“主机按运行时间付费，模型费用另计；关闭浏览器后任务继续运行；停止主机后
文件保留”。它没有给出所有失败路径或生产性能目标。不要从这几句话猜出完整收费公式，而要这样组织：

**云主机定价与计费：费用边界与计量依据**

- `BIL-01`：将材料中的费用边界写清楚：主机运行费用与模型调用费用分别归属各自计费对象。模型付费
  方式的变化不能被解释为主机免费；多个 Agent 使用同一主机时是否共享同一份运行计量，需要核对材料。
- `BIL-02 [建议]`：运行计量以主机实际可用状态为依据，不以浏览器在线时长计算。计量起止引用管理模块
  的就绪/停止定义；进入准备中或用户提交了停止请求，都不等于状态已经生效。未就绪、停止失败及状态
  待核实时的费用处理必须写明；建议按可核实的服务提供情况结算，具体边界待产品确认。
- `[待确认]`：停止后保留文件的费用、保留期限、计费粒度、舍入和预算是否涵盖保留成本。给出各方案
  的用户影响与成本取舍；若原型已经明确其中某项，则直接引用，不重新提出相反的收费方案。

**云主机管理：运行状态与保留后果**

- `HST-01`：以材料表达的“停止后文件保留”为起点，具体界定工作文件、配置、执行进程、内存和历史
  结果各自的后果；没有证据的部分标建议。停止完成后，Studio 能否续接旧任务、是否只能新建任务，
  必须与保留边界一致。
- `HST-02 [建议]`：停止请求未完成或结果未知时，向用户提供可识别状态和后续查询路径；不能提前承诺
  “已停止且不再计费”。最终状态确认后，同步影响 `BIL-02` 和 Studio 可执行条件。

**Studio Agents：连接与执行分离**

- `STU-01`：材料已表达离开浏览器不终止云端任务，需求应说明重新进入后如何识别同一任务与结果；
  前端连接失败不能直接等价为任务失败。主机确实停止时则服从 `HST-01` 的任务后果，而不是套用
  “后台继续运行”的承诺。
- `STU-02 [建议]`：任务结果不明时，先让用户能查询或辨认原任务状态，再决定重试；重试策略需说明
  是否可能创建新任务及再次消耗资源，不能把网络错误自动解释为执行从未发生。

这里的需求不是四份互不相干的页面说明：管理定义状态，计费解释该状态的经济含义，Studio 解释它对
执行的影响，市场负责提供符合执行条件的 Agent。更换页面布局不会改变这些业务关系。

### 7.3 跨模块验收示例

Given 一个已安装且满足执行条件的 Agent 正在可用主机上执行任务，When 用户关闭浏览器后重新进入，
Then 按材料中的任务连续性承诺，可以重新查询同一任务状态与结果；主机计量按主机状态延续，模型
费用仍由模型计费对象产生。具体查询时效按已确认的质量目标验收，不能从演示动画时长推定。

另行验证实际停止主机、停止失败、结果未知后恢复这几类与上述承诺相关的路径。它们的预期由对应
已确认规则决定；规则尚未确认时明确列为待确认验收条件，不伪造已通过的结果。

## 8. 完成标准

交付前针对本次范围检查；发现缺口后回到相关模块修订，不另交付内部检查表：

- **整体可读**：先交代产品目标、概念与模块关系；模块按业务职责组织，同一模块的子页面已合并理解。
- **真正补全**：模块含有策略、成立条件、业务规则、生命周期、异常或质量要求等实质内容；正文没有
  用布局/样式描述和点击流水账充数。必要的可见能力用业务语言交代，读者不必看图猜产品是什么。
- **有据有判断**：关键规则可定位依据；观察事实、已确认需求、建议与待确认项没有混淆。不把 mock、
  现有缺陷或缺失画面当作政策，也没有用一堆开放问题替代可评审的产品方案。
- **模块衔接**：共同规则只定义一次；状态、资格、时间、金额与数据后果在上下游一致，失败与恢复路径
  能贯通。必要约束已补齐，可选新能力明确在范围之外或作为建议。
- **可以验收**：重要规则有明确条件与预期；性能目标说明适用条件与依据，未确认的阈值和策略如实保留，
  文档草稿、已确认需求和实际测试结果不互相冒充。
- **产物可维护**：已有内容与历史未误覆盖，版本与引用有效，维护来源唯一，最终只交付对应 PRD。
  若有影响实施的未决项，最终回复点明其范围与推荐方案，不宣称已全部定稿。
- **截图和合并闭环**：关键图来自实际原型，保存前已忽略 Git，子文档均引用已上传的 OSS URL；
  最终文件由脚本生成，已完成对该版本全文及关键图的全局 review。问题已回改来源，重合并后的结果
  也已重新完整审阅，不能用脚本校验通过替代产品审阅。
