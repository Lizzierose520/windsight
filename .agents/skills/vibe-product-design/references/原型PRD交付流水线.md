# 模式 D · 子 PRD、关键截图、脚本合并与全局 review

模式 D 的产品分析方法见 [原型驱动 PRD](原型驱动PRD.md)。本文规定交付过程：**模型负责写作、判断与
审阅；脚本负责上传和确定性合并。最终交付物只有一份 `PRD.md`，子文档是持续维护的来源。**

## 1. 目录与唯一来源

```text
<project-dir>/
├── .gitignore                               # 截图前先加入下面的忽略规则
├── .context/vibe-product-design/screenshots/ # 在统一产出根下集中存放本地截图
│   └── <需求名>/
│       ├── 10-pricing-effective-time.png
│       └── 40-host-stop-impact.png
└── .context/vibe-product-design/<需求名>/
    ├── prd.config.json                      # 子文档、顺序及关键截图要求的唯一清单
    ├── 00-产品整体.md                       # 文档信息、变更记录、目标、术语和模块关系
    ├── 01-共同规则.md
    ├── 10-云主机定价.md                     # 同一业务模块的子页面/弹窗共同组织在这里
    ├── 20-智能体市场.md
    ├── 30-Studio-Agents.md
    ├── 40-云主机管理.md
    ├── 90-全局验收与质量.md
    ├── 99-待确认决策与来源.md
    ├── _prd-assets.json                     # 上传器记录内容摘要和公开 URL，不含凭据
    ├── _prd-source-map.json                 # 合并器记录输出摘要及源文件/行号
    ├── _review.md                          # 内部审阅记录，可选；不参与合并
    └── PRD.md                              # 脚本生成的唯一成稿，禁止直接编辑
```

截图、PRD 与配置共用 `.context/vibe-product-design/` 产出根；本地截图集中放在其中的 `screenshots/<需求名>/`，
不另建拼写不同的产出根或复制第二套文档。其他项目需要不同截图根目录时，
统一修改 `prd.config.json` 的 `screenshotsRoot`，也可使用上传器的 `--screenshots-root` 明确覆盖。

已有单文件 PRD 时，先完整读取并按业务模块迁入源文档，保留原有规则、版本历史和待确认项，核对迁移
完整后才首次生成覆盖 `PRD.md`。已有 A 分章文档可以直接注册为来源，但需整理为下面的标题规范；
选定一种合并方式持续维护，不让两个合并脚本轮流覆盖同一成稿。

## 2. 注册与撰写子文档

清单顺序就是最终阅读顺序，**不由模型在合并时重新编排，也不靠文件名猜应该有哪些模块**：

```json
{
  "schemaVersion": 1,
  "title": "Persistent Agents PRD",
  "screenshotsRoot": ".context/vibe-product-design/screenshots",
  "sections": [
    { "id": "overview", "file": "00-产品整体.md" },
    { "id": "policies", "file": "01-共同规则.md" },
    { "id": "pricing", "file": "10-云主机定价.md", "requireScreenshot": true },
    { "id": "market", "file": "20-智能体市场.md", "requireScreenshot": true },
    {
      "id": "studio",
      "file": "30-Studio-Agents.md",
      "requireScreenshot": true
    },
    { "id": "host", "file": "40-云主机管理.md", "requireScreenshot": true },
    { "id": "acceptance", "file": "90-全局验收与质量.md" },
    { "id": "decisions", "file": "99-待确认决策与来源.md" }
  ]
}
```

模块按实际范围增减。`requireScreenshot: true` 用于需要关键原型证据的业务模块，避免漏图后仍交付成功；
纯全局策略、术语或来源章节不用为凑数量配图。不能为了绕过缺图检查，把业务模块的要求改成 false。

- 每个源文件从**唯一的 `# 模块标题`**开始，内部使用 `##`、`###` 等 ATX 标题逐级展开，最多五级。
  不手写跨模块章节序号；合并器会添加全局章号并统一降低一级标题。业务规则 ID 保持稳定。
- 不在每个模块重复整个产品的封面、全局目录、变更记录。模块要有完整业务逻辑，并引用共同规则。
- 跨模块链接用真实源路径与标题，例如 `[停止的业务后果](40-云主机管理.md#停止与恢复)`；合并时自动
  转为最终文档内的对应锚点。图片只用标准 Markdown 图片语法，源文件中的代码示例不参与改写。
- 表格、业务图、公式、业务文案由模型在源文件里完成。需要格式化时对源文件使用
  `format_feature_prd.ts`，之后再合并；不要格式化或润色已生成的 `PRD.md`。

## 3. 截图前先忽略，截关键业务证据

先执行准备命令，**成功后才开始保存截图**：

```bash
node <skill-dir>/scripts/upload-prd-assets.mjs --project-dir <project-dir> --doc <需求名> --prepare
```

该命令保留已有 `.gitignore` 内容，幂等添加 `/.context/vibe-product-design/screenshots/*`，然后创建
本次需求的截图目录。若截图已经被 Git 跟踪，会明确失败：新增忽略规则不会自动取消已有跟踪，也不会
擅自操作暂存区。它不读取上传凭据、不联网、不上传文件。

观察、验收和截图统一使用原型开发时选定的标准视口；除非用户明确要求多端，不为截图另做手机、平板
或窄屏版本，不新增断点适配。单一视口的截图也不能被表述成已经完成多端验证。

截图选择围绕需要支持的产品结论：例如计费生效边界、资格与兼容限制、任务执行状态、停止后的影响。
**不截取全部页面、不为每个点击单独配图、不默认整页长截图。** 每张图应回答一个必要问题，重复画面
只保留最有信息的一张；同一证据可复用同一个 OSS URL。

1. 使用可用浏览器工具打开已开发的交互原型，实际操作到目标状态。确认是本地 mock 的交互再操作；
   真实环境遵循已有授权。使用现成登录态，不复制 Cookie 或代填密码。
2. 截取关键区域或元素，保留理解业务所必需的对象名称、单位、前置条件、结果状态和提示上下文。
   只使用实际原型截图，不用 AI 生成图冒充已开发界面。
3. 写入本需求截图目录，使用稳定可读的文件名，读图检查清晰度、裁剪范围和当前状态。截图中只保留
   固定模拟数据或已处理的非敏感内容；不要把真实密钥、客户信息、邮件正文上传到公共图床。
4. 将图放在对应规则或状态说明附近，先用相对源文档的本地路径引用，随后立即上传回写。图注只解释
   它支持的业务结论与规则编号，例如“图：变更申请与当前计费方式并存，对应 BIL-04 的延迟生效”。
   不描述颜色、位置、布局，不用图注替代页面没有展示的产品规则。

只有代码、没有可运行原型时，先完成可确定的源文档；已经提供的真实截图可以选择关键部分复用。
确实缺少可截图材料时明示缺口，不能伪造截图、声称交互已验证或宣称已取得最终成稿。

## 4. 上传后子 PRD 只留 OSS 地址

上传器与模式 B 共用；本仓库 `pnpm prd:assets` 也调用 skill 中这一份实现。默认使用公开的
Supabase Storage `prd-assets` bucket。截图属于公开可访问的产品证据，正文仍按仓库原来的权限阅读。

```bash
# 可选：只查看本需求将上传的对象，不联网、不修改文件
node <skill-dir>/scripts/upload-prd-assets.mjs --project-dir <project-dir> --doc <需求名> --dry-run

# 上传并回写子文档；模式 B 同一命令处理 assets/ 与 design/
node <skill-dir>/scripts/upload-prd-assets.mjs --project-dir <project-dir> --doc <需求名>

# 检查实际图片引用已经替换成可长期使用的 Storage URL
node <skill-dir>/scripts/upload-prd-assets.mjs --project-dir <project-dir> --doc <需求名> --check
```

读取项目环境中的 `SUPABASE_URL`（兼容 `NEXT_PUBLIC_SUPABASE_URL`），写入凭据使用
`SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_SECRET_KEY`；没有直接密钥时沿用
`SUPABASE_ACCESS_TOKEN` → Management API 的回退。仅用于本地上传，不写入客户端、PRD、日志或清单。
脚本使用 Node.js 20+ 的内置能力，不要求目标项目安装 Supabase SDK。

脚本先完整预检本地文件，再上传所引用的图片，以匿名 GET 核对图片类型及内容摘要；全部成功后回写
子文档并保存 `_prd-assets.json`。失败时保留原引用并返回错误，不能拿拼接出来的 URL 假装成功。
已有私有 bucket 不会被自动改公开。

对象键包含需求标识与内容摘要。截图换了内容，即使文件名不变，也上传到新地址并替换旧引用，避免 CDN
仍展示旧图；重复执行会复用同一内容。`--check` 也会检查有本地副本的已引用图片是否变化，避免换图后
漏传却仍通过检查。已有远程图在另一台机器上缺少本地副本时仍能阅读，不强制重新截图。
模式 D 只改清单中的源文档，**不直接改生成的 PRD.md**；回写后继续下一步合并。

## 5. 确定性脚本合并

```bash
node <skill-dir>/scripts/merge-prototype-prd.mjs <project-dir>/.context/vibe-product-design/<需求名>
```

算法直接按清单读取原文，添加全局标题层级和编号，改写跨子文档链接，生成目录，再拼接正文；保留业务
文案、表格、公式和 Mermaid/代码块，不调用任何大模型来总结、转写或“融合”正文。相同输入生成相同
字节，不插入每次都会变化的时间戳。输出固定为本需求目录的 `PRD.md`。

缺失文件、重复文件/id、越界路径、未列入清单的编号子文档、无效锚点、未上传图片或必需截图缺失时，
合并失败且保留上一份成稿。`_prd-source-map.json` 记录来源摘要、最终摘要、模块范围和标题行号。

```bash
# 检查当前成稿确实来自当前源文件，发现手改成稿或源文件修改后忘记合并
node <skill-dir>/scripts/merge-prototype-prd.mjs <需求目录> --check

# 将全局 review 发现的问题定位回源文件，例如最终文档第 150 行
node <skill-dir>/scripts/merge-prototype-prd.mjs <需求目录> --locate 150
```

## 6. 全局 review 必须形成闭环

**脚本成功不等于需求完整。模型必须完整阅读这一次实际生成的 PRD.md，再审阅其中的关键截图。**
长文可顺序分段读取，但要覆盖全文；只读目录、搜索关键词、检查差异或认为“各模块已经读过”都不算全局 review。

```text
子 PRD 写作与关键截图 → 上传并回写 OSS URL → 脚本合并
                                              ↓
                                      模型完整阅读本次 PRD
                                              ↓
                               是否仍有需要修正的实质问题？
                                  是 ↙                 ↘ 否
                        定位并修改原始子 PRD          校验后交付唯一 PRD.md
                          必要时重截受影响的图
                                  ↓
                         上传 → 脚本重合并 → 再完整阅读
```

每一轮检查整体定位、模块职责、共用规则、术语、状态、时间/金额口径、失败恢复、验收及图文一致性，尤其
注意“分别读都成立，放在一起却相互矛盾”的情况。问题按源文件和规则 ID 定位；共用策略回到定义处修改，
并同步受影响模块。结构问题改清单，事实或文案问题改源 Markdown，截图问题回到真实原型重新截取。

每次修改后都重新执行上传检查与脚本合并，模型再读**完整新成稿**，不能仅复查刚改的局部。不得手改
`PRD.md`，不得让另一个模型代替脚本拼接全文。内部可用 `_review.md` 记下本轮成稿 SHA-256、问题与
来源、修复和审阅结论；它不进入最终文档。变更记录只记录本次交付的实际产品变化，不把每轮校对当作新版本。

持续迭代，直到完整 review 没有发现尚未解决且能在当前授权范围内修正的实质问题，关键截图与文字一致，
图片检查和合并 `--check` 均通过。**不预设“改两轮就收工”**，也不为纯措辞偏好无限重写。
若仍缺产品决策、访问条件或材料，明确具体缺口和推荐方案，继续完成其他部分；不可伪造答案来宣布定稿。
影响实施的未决项存在时交付状态只能是待评审/待确认，不能声称是无遗留问题的最终版本。

最终校验的输出摘要应与最后一次完整 review 的摘要一致。若源文件、截图 URL 或清单又变化，旧 review
即失效，需要重合并并重新审阅。交付时只提供 `PRD.md`，说明本次覆盖范围、关键修改和真实剩余限制。

## 7. 脚本回归

```bash
node --test <skill-dir>/scripts/prd-workflow.test.mjs
```

测试使用临时目录和模拟 Storage，验证确定性合并、正文保留、源映射、遗漏/错误阻断、忽略规则、图片上传
与换图回写、失败时保留源文件、模式 B 兼容和重新合并链路，不访问生产 Storage。脚本测试不能代替模型的
全局产品审阅，也不能代替真实原型截图的视觉检查。
